What holds up well

The overall architecture is clean and the recent 0.3.x work shows. Things I would not change:

  • The compat shim (st_rsuite/_compat.py) is small, well documented, and resolves the isolate_styles registration-vs-call-site split once at import time. This is the right shape.
  • Lazy top-level imports in st_rsuite/__init__.py via module __getattr__, with rebinding so the hook fires once per name.
  • CI test matrix covers every supported Streamlit minor (1.51 through latest) with a browser-less smoke leg plus real Playwright e2e round-trips. This is the regression guard that caught the 0.3.3 floor bug, and it is solid.
  • Repo hygiene: built JS is gitignored and built fresh in CI, references/ and .claude/ stay untracked, and semantic-release keeps both pyproject versions in sync.
  • Locale handling: 29 locales mapped, with browser-language auto-detection and a sane language-only fallback chain.

Finding 1: PyPI wheel ships unminified dev builds

Severity: high. Verified against the actual v0.3.4 wheel downloaded from PyPI, not just inferred from the config.

build.mjs keys minification and sourcemaps off NODE_ENV === "production", but neither release.yml nor publish.yml ever sets it. npm does not set NODE_ENV for you. So every published release is a development build.

What is actually inside the v0.3.4 wheel:

  • 13 JS bundles, 19.5 MB total, unminified (largest: time_range_picker at 1.66 MB)
  • 13 sourcemaps, 30.3 MB total, shipped because sourcemap: !isProd is true in dev mode
  • ~50 MB unpacked into every user's site-packages; each widget serves ~1.6 MB of JS to the browser
Impact Every st-rsuite user downloads and serves roughly 5x more JavaScript than they need to. A page with five widgets ships ~8 MB of component JS before RSuite even renders. This is the single highest-leverage fix available.
Today: .github/workflows/release.yml (and publish.yml)
# NODE_ENV is unset, so build.mjs
# takes the dev path: no minify,
# sourcemaps on.
- run: npm ci && npm run build
  working-directory: st_rsuite/frontend

Result: 9.2 MB wheel, 49.8 MB unpacked.

Fix: make production the default, dev opt-in
// build.mjs: flip the default so a bare
// build is always production
const isProd = process.env.NODE_ENV !== "development";

// package.json already has build:dev and
// dev scripts for the development path

Also add recursive-exclude st_rsuite *.js.map to MANIFEST.in as a belt-and-suspenders guard.

Flipping the default in build.mjs is safer than adding env: blocks to the workflows, because it also protects any future workflow or a maintainer building a wheel locally. Worth adding a CI assertion too: fail the release if any build/*.js exceeds, say, 900 KB, so a regression can never ship silently again.

Finding 2: Python-side value changes never reach the widget

Severity: high (correctness). All 13 components use the exact "initial-only hydration" pattern that the repo's own CCv2 reference (references/state-sync.md) documents as a pitfall.

Every component seeds local React state from data.value with useState(initialValue) and never reconciles afterwards. The shared renderer reuses the same React root across reruns (WeakMap on parentElement), so re-renders keep the stale local state. Once a widget has mounted, changing value= from Python is silently ignored.

Concretely, none of these work today:

  • A "reset filters" button that re-runs the script with a different value=
  • Dependent widgets (picking a preset that should move a date picker)
  • Driving the widget from st.session_state per the canonical CCv2 controlled pattern
Today: all 13 *.tsx (DatePicker.tsx:64 shown)
const initialValue = useMemo(
  () => (value ? new Date(value + "T00:00:00") : null),
  [value]
);
// state never re-syncs after mount
const [selected, setSelected] =
  useState<Date | null>(initialValue);

Python re-runs with a new value; the widget keeps showing the old one.

Fix: reconcile from data, guard the echo
const lastEmitted = useRef<string | null>(null);

useEffect(() => {
  // only accept Python values we did not
  // just emit ourselves
  if (value !== lastEmitted.current) {
    setSelected(parse(value));
    lastEmitted.current = value;
  }
}, [value]);

// in handleChange:
lastEmitted.current = toISODate(next);

One shared hook (e.g. useSyncedValue) in shared/ covers all 13 components.

Note The lastEmitted guard matters: without it, the Python echo of the user's own selection can fight in-progress edits (the "fighting the user's cursor" problem the state-sync doc warns about). Add an e2e case: mount, click a Streamlit button that changes value=, assert the widget updated.

Finding 3: React and RSuite are bundled 13 times

Severity: medium. Real cost, but the fix is architectural, so it deserves its own release.

Each component is a separate Vite library build, and each bundle embeds its own full copy of React, ReactDOM, the RSuite runtime, all 29 locale files, and the react-icons subset. Even after Finding 1 is fixed (roughly 500 to 600 KB minified per bundle), an app using five st-rsuite widgets still downloads five copies of the same framework code, and the browser boots five independent React runtimes.

Two directions, not mutually exclusive:

  • Single registered component (recommended). Register one CCv2 component (one asset_dir, one bundle) and pass a kind discriminator in data; a top-level switch in the frontend routes to the right React component. One ~1 MB bundle, fetched once and cached for every widget on the page. Wheel drops to roughly 1 MB. The Python API does not change at all.
  • Cheaper trims if staying multi-bundle: lazy-load locales with dynamic import() instead of statically bundling all 29 into every component, and import react-icons per-icon (only Timeline needs them today).
Trade-off The single-component design gives up per-component cache invalidation (any change re-downloads the one bundle) and makes the one bundle bigger than any single current bundle. For a library where users typically mix several widgets per page, one shared cached bundle wins clearly.

API gaps vs RSuite v6

From the RSuite v6 docs sweep. The pattern: the wrappers expose appearance props well, but almost none of the constraint props. For a date/time library, constraints are core functionality, not polish.

Gap
Priority
Detail
No date constraints at all. shouldDisableDate, limitStartYear, limitEndYear
High
Even st.date_input has min_value/max_value. Callables do not cross the Python/JS boundary, so expose declarative params: min_date=, max_date=, disabled_dates=[...], disabled_weekdays=[...], and build the shouldDisableDate closure in JS.
No time constraints. shouldDisableHour/Minute/Second, hideHours/Minutes/Seconds
High
Business-hours pickers (a very common ask) are impossible today. Same declarative approach: min_time=, max_time=, hidden_hours=[...].
No shortcut ranges. DateRangePicker ranges
Med
RSuite ships Today / Yesterday / Last 7 days by default and supports custom presets. A ranges=[{"label": "Last 30 days", "value": (start, end)}] param is a big dashboard win.
No editable / loading.
Med
editable=False makes pickers toggle-only (kills keyboard-entry parse edge cases on touch devices); loading=True shows a spinner while the app computes.
No defaultCalendarValue / calendarDefaultDate.
Low
Controls which month the empty picker opens on. Cheap to add alongside the constraint work.
CheckTreePicker power props. virtualized, disabledItemValues, controlled expandItemValues
Low
virtualized=True matters for large trees; disabledItemValues complements the already-exposed uncheckable_values. (Async getChildren does not map to CCv2 cleanly; skip it.)
No datetime picker.
Med
RSuite DatePicker handles combined date+time via format="yyyy-MM-dd HH:mm", but the wrapper truncates everything to a date. A datetime_picker (or show_time=True) fills a real Streamlit hole: there is no native datetime input.

Smaller items

Scan the headings; expand what you care about.

Theme bridge misses high-contrast and RTL frontend/src/shared/theme.ts, renderer.tsx

RSuite's CustomProvider supports a third theme, high-contrast, which the bridge never emits, and an rtl prop that matters for the ar_EG and fa_IR locales you already ship. Both are one-line passes through CustomProvider. Also worth knowing: RSuite's provider default locale is en-GB, not en-US; your browser-detection fallback already handles this, so no change needed there.

Theme cache can go stale on live theme toggle frontend/src/shared/theme.ts:69

getStreamlitRsuiteTheme() only recomputes when --st-background-color changes and is only called when a rerun re-renders the component. If Streamlit ever repaints the theme without rerunning the script, mounted widgets keep the old mode. A MutationObserver on the root element's style attribute (or a matchMedia listener as backstop) would make it live. Low priority; verify whether a theme toggle triggers a rerun first.

carousel _resolve_src reads any file path it is handed st_rsuite/carousel/__init__.py:19

Any string that is not http/https/data is treated as a local path, expanded with ~, read, and inlined as a base64 data URI into the page. Fine when the app author controls src, but if an app ever passes user input through, it becomes an arbitrary-file-read-to-browser primitive. At minimum document that src must be trusted; optionally gate on an allowlist of image extensions.

Labels are not associated with their inputs all frontend/src/*/*.tsx

Each component renders <label> with no htmlFor, so screen readers do not connect the label to the control and clicking the label does nothing. Generate an id (React useId()) and pass it to the RSuite component's id prop.

Dead branch in date_picker._serialize st_rsuite/date_picker/__init__.py:78

The inner isinstance(d, datetime) check returns d.isoformat() on both paths; the branch is a no-op. Either delete it or make it meaningful by truncating datetimes to dates (d.date().isoformat()), which would also stop a passed datetime from leaking a time suffix into the frontend.

Missing Streamlit-parity conveniences: help=, width= all Python wrappers

Streamlit builtins take help= (tooltip) and are moving toward explicit width= params. A help= that renders an info tooltip next to the label would make the components feel native. You already have block= for full width; consider aliasing or documenting it against Streamlit's use_container_width vocabulary people search for.
